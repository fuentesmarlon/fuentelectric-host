1. Introducción

Este manual es para la persona que mantenga el sistema: corregir errores, hacer cambios, publicar nuevas versiones o atender un problema en producción. Se asume que conoce lo básico de JavaScript, Git y bases de datos. Para saber qué hace el sistema y sus reglas de negocio, lea primero la Documentación del sistema (FTE-TUR-DOC-01).

El código del proyecto también está comentado pensando en el mantenimiento. Cuando este manual mencione un archivo, abrirlo y leer su comentario inicial suele ser el mejor siguiente paso.

2. Arquitectura

Es una aplicación web Next.js desplegada en Vercel. No hay un backend separado: las páginas se generan en el servidor y los cambios (guardar, eliminar) se hacen con Server Actions que corren en el mismo servidor. Toda la información vive en PostgreSQL (Supabase) y se accede con Prisma.

Navegadoradmin o trabajador
→
Vercel · Next.jsproxy → páginas, acciones y /api
→
SupabasePostgreSQL · Auth
Next.js
→
Resendenvía el código de acceso
Sentryrecibe los errores
GitHub Actionsrevisa cada cambio (CI)

Recorrido de una petición

  1. Proxy (src/proxy.ts → src/utils/supabase/middleware.ts): renueva la sesión de Supabase y, si no hay sesión, manda al login.
  2. Página (src/app/tableros/<sección>/page.tsx): comprueba rol y vigencia de la sesión (lib/sesion.ts), consulta la base y entrega los datos al componente de pantalla.
  3. Componente de pantalla (*Client.tsx): formularios, filtros y diálogos en el navegador.
  4. Acción (actions.ts): al guardar, vuelve a comprobar que sea admin (lib/auth.ts), valida con las reglas de lib/reglas-turno.ts y escribe en la base dentro de una transacción. Devuelve null si todo salió bien o el texto del error.

5. Base de datos

TablaContenido y notas
UsuarioCuentas que pueden entrar. El id es el mismo de Supabase Auth. rol: SUPERADMIN, ADMIN o TRABAJADOR. debeCambiarContrasena: si está en true, debe elegir una contraseña nueva al entrar.
TrabajadorPersonal que recibe turnos: nombre, puesto (texto libre), estado, horario establecido y unidad fija opcional.
AreaZonas operativas. Nombre único y estado.
VehiculoUnidades: código único, tipo (CARRO/CAMION), capacidad (noPersonas) y estado.
TurnoDiarioUn turno. Guarda la relación con trabajador, área y vehículo y además una copia de sus nombres. Único por trabajador + fecha + jornada.
SnapshotTurnoAuditoría en texto, sin relaciones: sobrevive aunque el turno se borre.

Fechas de turno: la columna fecha se guarda a las 12:00 UTC del día (06:00 en Guatemala), así el día nunca cambia al convertir zonas horarias. Para buscar turnos de un día use rangoFechaTurno() de lib/form-validation.ts; no arme las fechas a mano.

Conexiones: la aplicación usa DATABASE_URL con el pooler de Supabase en modo transaction (puerto 6543) y un máximo de 5 conexiones por instancia (DATABASE_POOL_MAX). Las migraciones usan DIRECT_URL en modo session (puerto 5432).

Seguridad por filas (RLS): está activada en todas las tablas sin políticas, de modo que la API pública de Supabase no puede leer nada. La aplicación usa el rol postgres, que no se ve afectado.

6. Entornos y variables

Las variables se configuran en Vercel (Settings → Environment Variables) y, para trabajar en local, en un archivo .env (plantilla: .env.example). Nunca se suben al repositorio.

VariablePara qué sirve
NEXT_PUBLIC_ENTORNOproduccion, staging o desarrollo. Fuera de producción muestra una etiqueta en pantalla y separa los errores en Sentry.
DATABASE_URLConexión de la app (pooler, puerto 6543).
DIRECT_URLConexión para migraciones (puerto 5432).
NEXT_PUBLIC_SUPABASE_URL · NEXT_PUBLIC_SUPABASE_ANON_KEYProyecto de Supabase (públicas).
SUPABASE_SERVICE_ROLE_KEYClave secreta que genera los códigos de acceso. Solo en el servidor.
RESEND_API_KEYEnvío de correos con el código.
SENTRY_AUTH_TOKENOpcional: sube los source maps a Sentry al compilar.

Hoy el .env local del equipo de desarrollo apunta a la base de producción. Cualquier comando de base de datos que se ejecute en local (pnpm db:migrate, pnpm entrega …, Prisma Studio) cambia datos reales. Lo recomendado es crear un proyecto de Supabase de staging y usar ese en el .env.

7. Instalación local

  1. Instale Node.js 24 y pnpm 12, y clone el repositorio.
  2. Instale las dependencias (también genera el cliente de Prisma):
    pnpm install
  3. Copie .env.example a .env y complete los valores (de preferencia, de un proyecto de staging).
  4. Si la base está vacía, cree las tablas y, solo en staging, cargue datos de prueba:
    pnpm db:migrate
pnpm db:seed
  5. Inicie el servidor de desarrollo y abra http://localhost:3000:
    pnpm dev

8. Flujo de cambios y despliegue

Vercel publica automáticamente lo que llega a main. Por eso todo cambio pasa por una rama y un pull request:

  1. Cámbiese a main y actualícela (Fetch y Pull en GitHub Desktop).
  2. Cree una rama nueva desde main con un nombre descriptivo: fix/… para correcciones, feat/… para funciones nuevas, docs/… para documentación.
  3. Haga el cambio y verifique en local: pnpm lint, pnpm typecheck, pnpm test y pnpm build.
  4. Publique la rama y abra el pull request hacia main. GitHub Actions corre las mismas comprobaciones.
  5. Si el cambio necesita una migración, aplíquela antes de unir (sección 9).
  6. Una vez unido el PR, Vercel publica en uno o dos minutos. Revise la página en producción.

No use la rama dev: quedó atrasada respecto a main y los cambios hechos ahí generan conflictos. Si un PR muestra conflictos, lo más seguro es rehacer el cambio en una rama nueva desde main.

Volver a una versión anterior: en Vercel, Deployments → elija la última versión que funcionaba → Promote to Production (o Instant Rollback). Esto revierte el código, no la base de datos.

9. Migraciones de base de datos

Cada cambio de estructura de la base es una migración en prisma/migrations/. La última es 20261110120000_rol_superadmin. Revise con pnpm db:status cuáles faltan en producción.

  1. Modifique prisma/schema.prisma.
  2. Genere la migración contra una base de pruebas (nunca contra producción):
    pnpm prisma migrate dev --create-only --name descripcion_corta
  3. Revise el archivo migration.sql generado. Si quita valores o columnas, primero debe mover los datos existentes (vea 20261106180000_simplificar_estados como ejemplo).
  4. Revise qué falta aplicar en producción y aplíquelo antes de publicar el código que lo usa:
    pnpm db:status
pnpm db:migrate
  5. Una a main el PR con el código.

¿Por qué antes? El código anterior suele funcionar con la base ya migrada, pero el código nuevo puede fallar si la base todavía no tiene el cambio.

10. Cuentas y acceso

Una cuenta vive en dos lugares: el usuario en Supabase Auth (correo, contraseña y sesión) y su fila en la tabla Usuario (nombre y rol) con el mismo id. Las acciones de src/app/tableros/cuentas/actions.ts cambian los dos a la vez y, si el segundo paso falla, deshacen el primero.

RolPermisos y forma de entrar
SUPERADMINTodo lo de ADMIN y además la sección Cuentas de acceso. Contraseña o código; sesión de 1 hora.
ADMINTurnos, catálogos e historial. Contraseña o código; sesión de 1 hora.
TRABAJADORSolo el Dashboard. Solo código; sesión de 30 días.

Las reglas de permisos están en src/lib/roles.ts (esAdministrador, esSuperadmin). No compare el texto del rol a mano en el resto del código.

Crear, editar o eliminar una cuenta

Se hace desde el panel, con una cuenta de superadministrador: Cuentas de acceso. Ya no hace falta entrar a Supabase. El sistema aplica estas protecciones:

  • Nadie puede eliminarse ni cambiarse el rol a sí mismo.
  • Siempre debe quedar al menos un superadministrador.
  • Las cuentas de administrador necesitan contraseña (mínimo 8 caracteres); además pueden entrar con código.
  • Si un correo ya existía en Supabase Auth sin fila en Usuario (una cuenta a medias), al crearla se reutiliza.

Cambio de contraseña obligatorio

La columna Usuario.debeCambiarContrasena la activa el superadministrador con la casilla Pedir cambio de contraseña al iniciar sesión (al crear la cuenta o al editarla). Mientras esté en true:

  • Al iniciar sesión (con contraseña o con código) la persona va a /cambiar-contrasena en lugar de /tableros.
  • requerirSesion (src/lib/sesion.ts) la regresa ahí desde cualquier página del panel, y verificarAdmin / verificarAdminApi (src/lib/auth.ts) rechazan sus acciones y descargas.
  • La contraseña nueva se guarda con la sesión de la propia persona (supabase.auth.updateUser), así Supabase aplica sus reglas y la sesión sigue abierta. Después la columna vuelve a false.

Solo aplica a administradores y superadministradores; en una cuenta de trabajador la casilla no aparece y el valor se guarda en false.

Si no queda ningún superadministrador

Solo pasaría si alguien cambia la base a mano. Se recupera desde Supabase → SQL Editor:

update "Usuario" set rol = 'SUPERADMIN' where email = 'correo@fuentelectric.com';

Otras operaciones

  • Restablecer la contraseña de un admin: en Cuentas de acceso → editar → marcar Pedir cambio de contraseña al iniciar sesión. La persona entra con código por correo y elige la nueva. Si se prefiere, también se le puede escribir una contraseña temporal en Nueva contraseña.
  • Quitar un cambio pendiente sin que lo haga: editar la cuenta y desmarcar la casilla, o en el SQL Editor: update "Usuario" set "debeCambiarContrasena" = false where email = 'correo@fuentelectric.com';
  • Quitar el acceso: eliminar la cuenta en Cuentas de acceso. Se borra de Supabase Auth y de Usuario, y se cierran sus sesiones. Los turnos y la auditoría no se ven afectados.

Valores de seguridad que se pueden ajustar

ValorDónde
Duración de la sesión (1 hora administradores / 30 días trabajador)src/lib/auth.ts
Intentos de inicio de sesión y códigos por correoConstantes al inicio de src/app/login/actions.ts

El límite de intentos se guarda en la memoria de cada instancia del servidor. Frena el abuso casual, pero no es un límite global; si se necesitara, habría que usar un almacén compartido (por ejemplo, una tabla o Redis).

11. Monitoreo y registros

  • Sentry recibe los errores del navegador, del servidor y del proxy, separados por entorno. Configuración: src/instrumentation-client.ts, sentry.server.config.ts y sentry.edge.config.ts. Recomendado: crear una alerta por correo para errores nuevos en Alerts → Create Alert.
  • Vercel → Logs muestra los mensajes del servidor (por ejemplo, si falló el envío de un correo).
  • Supabase → Reports muestra el uso de la base y las conexiones.
  • Resend → Emails muestra si cada correo de código se entregó o rebotó.

12. Respaldos y recuperación

  • Revise en Supabase (Database → Backups) qué respaldos automáticos incluye el plan contratado y por cuántos días se guardan.
  • Para un respaldo propio de toda la base, use pg_dump con la conexión de DIRECT_URL y guarde el archivo en un lugar seguro de la empresa:
    pg_dump "$DIRECT_URL" --no-owner --format=custom --file=respaldo-AAAA-MM-DD.dump
  • Los reportes de Historial (Reporte Completo en Excel) sirven como respaldo legible de la programación de un periodo.
  • pnpm entrega respaldar copia los catálogos (áreas, vehículos, trabajadores y usuarios) a la carpeta respaldos/, que no se sube a Git porque contiene datos personales.

No ejecute pnpm entrega limpiar. Borra todas las asistencias y el historial; solo se usó para dejar la base limpia antes de la entrega.

16. Buenas prácticas de seguridad

  • Las claves (SUPABASE_SERVICE_ROLE_KEY, RESEND_API_KEY, conexiones) solo van en Vercel y en el .env local; nunca en el código, en capturas ni en chats.
  • Toda acción nueva que cambie datos debe empezar con verificarAdmin() (o verificarSuperadmin() si es de cuentas), y toda página de administración con requerirAdminPagina().
  • Mantenga al menos dos administradores activos para no quedarse sin acceso.
  • Cuando alguien deje la empresa, quite su acceso el mismo día (sección 10).
  • La carpeta respaldos/ tiene datos personales: no la comparta ni la suba a Git.
